# ADR 0002: Стратегия чтения и безопасной записи StrictDoc

- Статус: принято
- Дата: 2026-09-02
- Область: P0

## Контекст

Пользователь должен редактировать требования через структурированную форму, но `.sdoc`
остаётся каноническим форматом. Нужно сохранять многострочный Unicode-текст, MID, UID,
relations, неизвестные поля и порядок секций. Ошибка проверки, конкурентная запись или
сбой процесса не должны повреждать проект. Собственный parser, regex-patching и
собственный ReqIF-конвертер запрещены.

## Решение

### Чтение

Каждое обновление индекса выполняется под файловой блокировкой:

1. StrictDoc `0.29.0` запускается списком аргументов через `subprocess.run`, с
   `shell=False`, ограниченным timeout и временным output-каталогом;
2. используется штатный JSON export;
3. проверяются return code, stderr и наличие ожидаемых файлов;
4. JSON нормализуется в domain-модель;
5. вычисляется revision по каноническим входам;
6. обновляется только производный кеш.

Диагностика команды, длительность и хеши результатов сохраняются отдельно от
канонических файлов. JSON никогда не редактируется и не используется как вход для записи.

### Запись

Запись разрешена только для документов, перечисленных в
`strictdoc.managed_documents` файла `project.yaml`. Writer использует parser/model API и
serializer закреплённого StrictDoc `0.29.0`; regex и текстовые подстановки не применяются.

Алгоритм изменения:

1. нормализовать путь и убедиться, что он находится в корне проекта и в allowlist;
2. проверить `If-Match` относительно текущего revision;
3. получить эксклюзивный project lock и повторно проверить revision;
4. разобрать полный проект через grammar/model API StrictDoc;
5. изменить только адресованный узел и сериализовать candidate;
6. собрать полный временный проект с candidate в том же файловом томе;
7. выполнить штатную валидацию и JSON export временного проекта;
8. при любой ошибке удалить candidate и вернуть структурированную диагностику, не
   касаясь исходника;
9. создать backup исходного файла в `.reqpilot/backups`, применяя ограниченную ротацию;
10. заменить исходный файл атомарным `os.replace`;
11. перестроить индекс и вернуть новый revision.

Если непредвиденная ошибка возникает после замены, writer восстанавливает последний
backup атомарно под тем же lock и повторно валидирует проект. Явный rollback использует
тот же путь: candidate из backup сначала проверяется во временном полном проекте, затем
применяется через `os.replace`.

Инварианты:

- MID и UID существующего узла не меняются;
- новое требование получает новый MID, а удалённый UID не переиспользуется;
- relations и неизвестные поля сохраняются;
- порядок документов и секций стабилен;
- два клиента с одним revision не могут молча перезаписать друг друга;
- невалидный candidate никогда не становится каноническим файлом.

Штатные HTML, PDF, XLSX, JSON и ReqIF экспорты запускаются отдельным сервисом тем же
безопасным способом. ReqIF не постобрабатывается собственным конвертером.

## Рассмотренные альтернативы

### Regex-patching `.sdoc`

Отклонено: не учитывает grammar, escaping, многострочные значения, повторяющиеся поля и
relations; легко меняет не тот узел.

### Пересобрать документ собственным шаблоном

Отклонено: неизвестные поля и будущие конструкции StrictDoc могли бы потеряться молча.

### Записать файл, затем проверить и при ошибке откатить

Отклонено: между записью и откатом другие процессы увидят невалидный проект. Валидация
candidate должна происходить до атомарной замены.

### Использовать JSON export для обратной генерации `.sdoc`

Отклонено: экспорт не является lossless write-моделью и стал бы вторым форматом
хранения.

## Последствия

Положительные:

- все синтаксические правила делегированы точной версии StrictDoc;
- конкурентные изменения обнаруживаются как revision conflict;
- сбой до `os.replace` не повреждает исходник;
- backup обеспечивает проверяемый ручной и автоматический rollback.

Отрицательные:

- полная временная валидация дороже прямой записи;
- write API жёстко связан с совместимостью StrictDoc `0.29.0`;
- новый тип узла или grammar требует отдельного compatibility test.

## Проверка решения

Compatibility spike и интеграционные тесты обязаны доказать сохранность многострочного
Unicode, MID, UID, relations и неизвестных полей, успешную повторную валидацию,
конфликт двух revision и неизменность исходного SHA-256 при искусственной ошибке.
