# ADR 0004: Межсистемные связи и единый граф

- Статус: принято
- Дата: 2026-09-02
- Область: P0

## Контекст

StrictDoc владеет требованиями, а Capella — архитектурой. Межсистемная связь должна
переживать переименование архитектурного объекта, обнаруживать удаление объекта и
участвовать в графе, матрицах и impact analysis. Она не должна требовать записи модели
Capella в P0.

## Решение

`trace-links.yaml` является единственным каноническим хранилищем связей
«требование ↔ архитектура». Запись выполняется через `ruamel.yaml` под lock,
с временным candidate, валидацией, backup и `os.replace`, чтобы сохранить порядок и
читаемый Git diff.

Каждая связь содержит:

- уникальный стабильный link ID;
- MID требования как стабильный ключ и UID как проверяемый snapshot;
- `model_id` и UUID Capella как стабильный архитектурный ключ;
- `name_snapshot` только для удобства человека;
- тип relation и служебные сведения схемы.

Пара `MID + model_id + UUID + relation` уникальна. MID и UID должны разрешаться в
актуальном StrictDoc index. UUID должен разрешаться в выбранном live или fixture index.
Переименование Capella-объекта не меняет link ID и не ломает связь; отдельная явная
операция обновляет `name_snapshot`. Не найденный UUID превращает связь в `broken`, но не
удаляется автоматически.

Unified graph — производное представление трёх источников:

- узлы StrictDoc (requirements и TestCase);
- узлы Capella;
- placeholder для неразрешённого UUID;
- рёбра StrictDoc relations, отношений/allocations Capella и `trace-links.yaml`.

Идентификаторы узлов имеют namespace (`req:<MID>`,
`capella:<model_id>:<UUID>`, `broken:<model_id>:<UUID>`), поэтому коллизии источников
невозможны. Нормализация и сортировка детерминированы. GraphService применяет filter,
connected-component focus и depth 1–4 до передачи данных frontend; полный граф не
рендерится по умолчанию.

Четыре матрицы (requirements↔tests, requirements↔functions,
requirements↔components и functions↔components), coverage и impact analysis вычисляются
из того же snapshot unified graph. CSV матрицы является производным экспортом текущего
фильтра. Отдельных таблиц связей или скрытых правил покрытия не создаётся.

## Рассмотренные альтернативы

### Связывать Capella по имени

Отклонено: имя не уникально и меняется при обычном рефакторинге. UUID является
стабильным идентификатором модели.

### Использовать только UID требования

Отклонено: принятый внешний ключ ReqPilot — MID; UID сохраняется рядом как понятный
snapshot и дополнительная проверка рассогласования.

### Зеркалировать links внутрь Capella в P0

Отклонено: нарушает read-only границу. Контролируемая очередь Python4Capella относится
только к P1 после завершения P0.

### Удалять broken links автоматически

Отклонено: это скрывает потерю архитектурного объекта и уничтожает диагностическую
информацию. Исправление или удаление всегда является явным действием пользователя.

### Отдельная реализация каждой матрицы

Отклонено: четыре независимых набора join-правил быстро разойдутся с графом и impact
analysis. Все представления должны читать один immutable snapshot.

## Последствия

Положительные:

- переименование объекта не ломает трассировку;
- удаление выявляется и остаётся видимым;
- граф, матрицы, coverage и impact дают согласованные результаты;
- YAML остаётся понятным человеку и хорошо просматривается в Git.

Отрицательные:

- snapshot имени может устареть и требует отдельного refresh;
- внешняя связь не является транзакцией двух инженерных инструментов;
- перестроение unified graph должно инвалидироваться при изменении любого из трёх
  fingerprints.

## Проверка решения

- тест переименования сохраняет link ID и статус `valid` при том же UUID;
- тест удаления получает placeholder и `broken`, не меняя YAML автоматически;
- duplicate test отклоняет одинаковую ключевую пару;
- тесты матриц и impact используют один graph revision и deterministic ordering;
- performance test формирует отфильтрованный граф для 300 требований, 1 000 элементов и
  2 000 рёбер менее чем за одну секунду на обычной рабочей станции.
