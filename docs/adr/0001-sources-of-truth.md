# ADR 0001: Архитектура и источники истины

- Статус: принято
- Дата: 2026-09-02
- Область: P0

## Контекст

ReqPilot должен дать единое представление требований, архитектуры и тестов, не становясь
ещё одной RMS и не подменяя StrictDoc или Eclipse Capella. Одни и те же сущности доступны
через несколько представлений: web-интерфейс, JSON-индексы, граф, матрицы и отчёты. Без
явной границы канонических и производных данных эти представления неизбежно начнут
расходиться.

## Решение

Применяется следующая модель владения данными:

| Данные | Единственный источник истины |
|---|---|
| Текст, атрибуты, внутренние связи требований и TestCase | управляемые файлы StrictDoc `.sdoc` |
| Архитектурные элементы, отношения и allocations | файлы модели Eclipse Capella |
| Диаграммы | Capella `.aird` |
| Связи «требование ↔ архитектура» | `trace-links.yaml` |
| JSON-индексы, кеши, граф, матрицы и отчёты | только производные данные |

Backend строится как набор независимых слоёв:

1. adapters обращаются к StrictDoc, Capella, YAML и Git;
2. domain содержит нормализованные сущности и правила без зависимости от FastAPI;
3. services строят граф, матрицы, impact analysis и экспорты;
4. FastAPI публикует REST API и собранный frontend.

Зависимости передаются явно; глобальное изменяемое состояние не используется. Frontend
не хранит канонические требования или связи в `localStorage`. Он получает revision и
производные представления от backend и отправляет изменения только через API.

В P0 действуют дополнительные границы:

- сервер слушает только `127.0.0.1`, произвольный CORS не включается;
- StrictDoc остаётся единственным механизмом проверки и штатного экспорта требований;
- ReqIF создаётся только штатной командой StrictDoc;
- файлы Capella читаются, но никогда не изменяются;
- все пути разрешаются относительно корня проекта и проверяются на выход за него.

## Рассмотренные альтернативы

### Общая SQLite/PostgreSQL-база

Отклонено: потребовало бы двусторонней синхронизации, миграций и правил разрешения
конфликтов, а ReqPilot превратился бы в отдельную RMS.

### JSON-индекс как каноническое хранилище

Отклонено: JSON export StrictDoc предназначен для чтения и может быть полностью
перестроен. Редактирование индекса создало бы второй источник истины.

### Хранить межсистемные связи внутри `.sdoc` или Capella

Отклонено для P0: это смешивает зоны владения, требует записи Capella либо расширяет
StrictDoc специфичными для одной модели данными. Отдельный YAML можно проверить и
версионировать независимо.

## Последствия

Положительные:

- каждый тип данных имеет одного владельца;
- кеши и отчёты можно удалять и воспроизводить;
- отказ web-приложения не блокирует работу штатных инструментов;
- границы записи легко проверяются тестами.

Отрицательные:

- для согласованного экрана требуется индексировать несколько источников;
- обновления не образуют единую транзакцию между StrictDoc, Capella и YAML;
- frontend обязан явно показывать stale/error/fixture состояния, а не маскировать их.

## Проверка решения

- тесты удаляют производные кеши и воспроизводят одинаковые индексы;
- поиск по репозиторию не обнаруживает запись канонических данных в БД или
  `localStorage`;
- тесты API подтверждают bind на loopback и отсутствие широкого CORS;
- SHA-256 файлов Capella до и после всех P0-операций совпадает.
